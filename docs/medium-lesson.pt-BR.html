Criando um Chatbot com Flutter e DialogFlow

Notas de aula do prof. Kleber de Oliveira Andrade — revisão de 17 de novembro de 2026.

Nesta aula vamos construir e compreender uma interface de conversa com Flutter, separar as regras das mensagens da interface e relacionar o exemplo aos conceitos de intents e entidades do Dialogflow ES. Você poderá executar e testar o projeto sem conta na nuvem. Depois, estudaremos o caminho de uma integração remota segura.

Mudança importante em relação à aula de 2019: não colocamos mais uma chave de conta de serviço em assets/credentials.json. Uma chave distribuída em um aplicativo pode ser extraída. O exemplo atual é uma demonstração local, com regras explícitas; ele não faz consultas ao Dialogflow, não treina um modelo e não é IA generativa. Nenhum servidor remoto foi implementado ou validado nesta revisão.

1. O que um chatbot faz?

Um chatbot oferece uma interface de conversa para uma tarefa delimitada: consultar cursos, encontrar instruções ou responder perguntas frequentes. Uma conversa útil não precisa fingir ser humana; precisa explicar suas capacidades, reconhecer limites e oferecer recuperação quando não entende uma pergunta. O tutor desta aula se apresenta como demonstração local e responde com um fallback quando não encontra uma regra.

O contexto histórico continua relevante: a pergunta de Alan Turing sobre máquinas e inteligência inspirou pesquisas posteriores em conversação. Nosso exercício, porém, avalia comportamentos observáveis de um programa, sem usar o Teste de Turing como requisito de qualidade e sem atribuir compreensão humana às regras locais.

2. Agente, intent, entidade e sessão

No Dialogflow ES, o agente reúne a configuração da conversa. Uma intent classifica o objetivo de uma mensagem; frases de treinamento exemplificam maneiras de pedir a mesma coisa. Uma entidade descreve um tipo de valor a extrair. O parâmetro recebe o valor extraído. Contextos permitem restringir intents conforme o estado de uma conversa. A sessão identifica uma conversa, e não deve ser compartilhada entre usuários.

Em “Quero aprender Flutter”, o objetivo pode ser consultar um curso; a entidade course tem o valor Flutter. Na implementação local, mostramos intent: course e course: Flutter para tornar o resultado visível. Esses rótulos vêm de comparações no código. No Dialogflow, classificação e extração são realizadas pelo agente configurado. Uma regra por substring não tem a generalização do NLU e pode interpretar mal negações ou perguntas com vários assuntos.

5. Uma fronteira clara para as respostas

Comece pelo contrato Tutor. Ele recebe uma pergunta e devolve BotReply com texto, intent e entidades. A interface permite trocar o mecanismo de resposta sem misturar autenticação e widgets. LocalTutor mantém classify como função pura: a mesma entrada produz o mesmo resultado. Este é o arquivo completo lib/domain/local_tutor.dart:

/// The integration boundary. A remote implementation must call your own server.
abstract interface class Tutor {
  Future<BotReply> reply(String text);
}
class BotReply {
  const BotReply(this.text, this.intent, [this.entities = const {}]);
  final String text;
  final String intent;
  final Map<String, String> entities;
}
/// Deterministic teaching rules. This does not call or emulate Dialogflow NLU.
class LocalTutor implements Tutor {
  const LocalTutor();
  @override
  Future<BotReply> reply(String text) async => classify(text);
  BotReply classify(String text) {
    final query = text.toLowerCase();
    if (RegExp(
      r'(^|\s)(oi|ola|olá|bom dia|boa tarde|boa noite)(?=\s|[!?. ,]|$)',
    ).hasMatch(query)) {
      return const BotReply(
        'Olá! Sou o tutor local. Pergunte sobre Flutter, intents ou entidades.',
        'greeting',
      );
    }
    if (query.contains('intent') || query.contains('intenç')) {
      return const BotReply(
        'Uma intent representa o objetivo de uma mensagem. Exemplo: consultar um curso. '
            'Aqui usamos regras explícitas; no Dialogflow você fornece frases de treinamento.',
        'intent',
      );
    }
    if (query.contains('entidad') || query.contains('entit')) {
      return const BotReply(
        'Uma entidade identifica um valor na frase. Em “quero aprender Flutter”, '
            'o curso é Flutter. Experimente essa frase!',
        'entity',
      );
    }
    if (query.contains('flutter') || RegExp(r'\bdart\b').hasMatch(query)) {
      final course = query.contains('flutter') ? 'Flutter' : 'Dart';
      return BotReply(
        '$course é um dos temas desta aula. Comece pelo README do projeto e execute os testes. '
            'Esta resposta veio de uma regra local, sem consulta externa.',
        'course',
        Map.unmodifiable({'course': course}),
      );
    }
    if (query.contains('dialogflow') || query.contains('seguran')) {
      return const BotReply(
        'Uma integração real passa pelo seu servidor autenticado, que chama o Dialogflow. '
            'Nunca inclua uma chave de serviço no app. Este demonstrador não usa a nuvem.',
        'integration',
      );
    }
    if (query.contains('obrigad')) {
      return const BotReply(
        'De nada! Continue explorando e testando.',
        'thanks',
      );
    }
    if (query.contains('ajuda')) {
      return const BotReply(
        'Experimente: “O que é uma intent?”, “O que é uma entidade?” ou '
            '“Quero aprender Flutter”. As regras são limitadas e estão no código.',
        'help',
      );
    }
    return const BotReply(
      'Ainda não tenho uma regra para essa pergunta. Tente perguntar sobre '
          'Flutter, intents, entidades ou Dialogflow.',
      'fallback',
    );
  }
}

As regras têm precedência: saudação, explicação de intent, explicação de entidade, curso, integração, agradecimento, ajuda e fallback. Observe a diferença entre responder sobre entidades e extrair um curso. Essa ordem é uma decisão didática explícita; ela não constitui um classificador geral de linguagem natural. Para evoluir o domínio, primeiro acrescente exemplos positivos e negativos nos testes.

6. Mensagens e o ciclo de uma conversa

Cada ChatMessage possui ID, texto, autor e instante. As respostas também podem trazer intent e entidades. A lista conserva a ordem de inserção; não ordenamos pelo relógio, que pode repetir horários ou mudar. A cópia não modificável impede que a tela altere o histórico por fora do controlador. Este é o arquivo completo lib/domain/conversation.dart:

import 'dart:async';
import 'package:flutter/foundation.dart';
import 'local_tutor.dart';
export 'local_tutor.dart' show BotReply, Tutor;
enum Author { you, tutor }
class ChatMessage {
  const ChatMessage({
    required this.id,
    required this.text,
    required this.author,
    required this.time,
    this.intent,
    this.entities = const {},
  });
  final int id;
  final String text;
  final Author author;
  final DateTime time;
  final String? intent;
  final Map<String, String> entities;
}
/// One writer, one in-flight turn. Generation invalidates reset/disposed work.
class Conversation extends ChangeNotifier {
  Conversation({
    required this.tutor,
    DateTime Function()? clock,
    this.timeout = const Duration(seconds: 15),
  }) : _clock = clock ?? DateTime.now;
  static const maxCodePoints = 500;
  final Tutor tutor;
  final DateTime Function() _clock;
  final Duration timeout;
  final List<ChatMessage> _messages = [];
  List<ChatMessage> get messages => List.unmodifiable(_messages);
  bool _isSending = false;
  bool get isSending => _isSending;
  String? _error;
  String? get error => _error;
  int _generation = 0;
  int _nextId = 0;
  bool _disposed = false;
  static bool validText(String text) =>
      text.trim().isNotEmpty && text.trim().runes.length <= maxCodePoints;
  Future<bool> send(String text) async {
    if (_disposed || _isSending || _error != null || !validText(text)) {
      return false;
    }
    final clean = text.trim();
    _messages.add(
      ChatMessage(
        id: _nextId++,
        text: clean,
        author: Author.you,
        time: _clock(),
      ),
    );
    await _respond(clean);
    return true;
  }
  Future<void> retry() async {
    if (_disposed || _isSending || _error == null) return;
    await _respond(_messages.last.text);
  }
  Future<void> _respond(String text) async {
    final generation = _generation;
    _isSending = true;
    _error = null;
    notifyListeners();
    try {
      final answer = await tutor.reply(text).timeout(timeout);
      if (!_current(generation)) return;
      if (answer.text.trim().isEmpty) {
        throw const FormatException('Empty reply');
      }
      _messages.add(
        ChatMessage(
          id: _nextId++,
          text: answer.text.trim(),
          author: Author.tutor,
          time: _clock(),
          intent: answer.intent,
          entities: Map.unmodifiable(answer.entities),
        ),
      );
    } catch (_) {
      if (!_current(generation)) return;
      _error =
          'Não foi possível responder. Tente novamente ou reinicie a conversa.';
    } finally {
      if (_current(generation)) {
        _isSending = false;
        notifyListeners();
      }
    }
  }
  bool _current(int generation) => !_disposed && generation == _generation;
  void reset() {
    if (_disposed) return;
    _generation++;
    _messages.clear();
    _isSending = false;
    _error = null;
    notifyListeners();
  }
  @override
  void dispose() {
    _disposed = true;
    _generation++;
    super.dispose();
  }
}

send remove espaços externos, rejeita mensagens vazias e limita a entrada a 500 pontos de código Unicode. Isso não é o mesmo que 500 caracteres visuais: um emoji composto pode usar vários pontos. O contador da interface usa a mesma regra. Só uma resposta pode estar pendente. Se houver erro, a pessoa escolhe tentar novamente ou reiniciar; retry responde à mesma mensagem sem acrescentar outra bolha de usuário.

O prazo de 15 segundos evita um estado de envio indefinido. Resposta vazia também vira uma falha recuperável. Não exibimos detalhes brutos de exceções. A geração da conversa muda em reset e dispose: uma resposta antiga é ignorada mesmo se a operação original terminar depois. Isso invalida o resultado; não cancela fisicamente uma futura chamada de rede. Para ações remotas, idempotência e cancelamento precisam ser tratados também no servidor.

8. Como planejar um agente no Dialogflow ES

A etapa local está pronta sem criar contas. Se você já tem um projeto autorizado para estudar Dialogflow ES, consulte o guia oficial de configuração e as condições de preço e permissões antes de ativar serviços. Esta revisão não cria projeto, conta, cobrança, chave, permissão nem deploy. As instruções seguintes descrevem um desenho de agente; nenhum agente remoto foi treinado ou testado aqui.

No console do Dialogflow ES, escolha um agente de estudo com idioma pt-BR e fuso apropriado. Mantenha uma intent de boas-vindas e uma de fallback. Crie a intent course.lookup e acrescente frases de treinamento como “Quero aprender Flutter”, “Tem curso de Dart?” e “Quero estudar Flutter”. Evite usar informações profissionais antigas do professor como dados atuais do bot.

Crie o tipo de entidade course com valores canônicos Flutter e Dart; você pode cadastrar sinônimos pertinentes ao seu domínio. Nas frases, anote a palavra do curso como parâmetro course desse tipo. Uma resposta de estudo pode usar “Você escolheu $course. Consulte o material do curso.” Se o curso for obrigatório, configure a coleta desse parâmetro e uma pergunta de esclarecimento. Salve e experimente variações no simulador do console, além de perguntas fora do domínio. Registre o objetivo esperado, o valor extraído e o resultado observado; não presuma que toda variação será compreendida.

A intent remota course.lookup e o rótulo local course têm papéis equivalentes neste exemplo, mas nomes e implementação são independentes. As regras locais não são exportadas automaticamente para o Dialogflow, e o app atual não consulta o simulador do console.

9. Integração real: credenciais no servidor

O fluxo proposto é: aplicativo Flutter → seu servidor autenticado → API Dialogflow ES v2 → seu servidor → aplicativo. Um futuro adaptador Tutor chamaria o servidor da sua aplicação. Ele não receberia a chave do Google e não autenticaria uma conta de serviço no dispositivo. Nenhum endpoint desse servidor existe neste repositório.

O servidor deve identificar e autorizar a pessoa, validar novamente a mensagem, limitar frequência e tamanho e manter uma sessão por conversa. Ele cria um ID de sessão do Dialogflow com até 36 bytes, sem reutilizá-lo para usuários diferentes. Com uma identidade de workload e Application Default Credentials, chama Sessions.detectIntent com text e languageCode pt-BR e traduz intent, parâmetros e resposta para um contrato próprio. Prefira identidades gerenciadas ou federação a chaves permanentes e use apenas as permissões necessárias.

Um contrato possível para o seu servidor é POST /v1/conversations/{conversationId}/messages, com requestId e text. A resposta contém reply, intent e valores de entidades validados. O servidor mantém a relação entre usuário autenticado, conversa e sessão Google; não aceite um caminho arbitrário de projeto/sessão fornecido pelo cliente. Defina prazos, CORS, tamanho máximo das respostas e política de retenção. Evite registrar o conteúdo da conversa sem necessidade e consentimento.

O bloqueio de duplo clique do app não evita efeitos duplicados no serviço: se o cliente expirar e tentar de novo, a primeira chamada pode já ter sido processada. Use requestId e armazenamento de resultados no servidor para garantir idempotência de ações de negócio. Reiniciar precisa também invalidar a sessão remota. A documentação técnica detalha essa fronteira proposta e os limites ainda não validados.

Se você seguiu a versão antiga e distribuiu uma chave real dentro do aplicativo, trate-a como exposta: o proprietário deve revogar ou rotacionar a chave no Google Cloud e revisar os registros de acesso. Apagar o arquivo de um commit novo não revoga a credencial. Não usamos, reproduzimos nem rotacionamos chaves nesta atualização. Arquivos de ambiente, ofuscação e --dart-define também não protegem um segredo embarcado no cliente.

O resultado deve ser conferido no workflow real, sem inventar percentuais de cobertura. crapper, dryer e mutator estão instalados, mas seus formatos suportados não incluem Dart; por isso não relatamos pontuações dessas ferramentas.

Android e iOS tiveram os modelos atualizados; builds nativos, aparelhos físicos, VoiceOver e integração externa permanecem não verificados. As licenças Android pendentes não foram aceitas. Não houve ativação de serviço pago, publicação de pacote nem deploy. O registro de validação informa os comandos e limites para repetir os testes.

Cinco exercícios práticos

  1. Bolhas e contraste. Objetivo: distinguir visualmente a resposta de fallback sem depender só da cor. Critério de conclusão: manter autor/data legíveis em 360 pixels com texto 2× e adicionar um teste de widget que reconheça o estado.
  2. Datas e ordenação. Objetivo: agrupar mensagens por dia com um separador. Critério de conclusão: um teste que atravesse a meia-noite deve mostrar as duas datas e preservar a ordem de inserção, mesmo com horários repetidos.
  3. Campo e teclado. Objetivo: permitir Shift+Enter para nova linha e Enter para enviar. Critério de conclusão: testes de teclado comprovam ambas as ações, preservam o limite de 500 pontos Unicode e rejeitam texto composto apenas por espaços.
  4. Dez intents para outro domínio. Objetivo: modelar um novo assistente de estudo com dez objetivos diferentes. Critério de conclusão: cada intent tem três frases de exemplo, resposta e caso fora do domínio; uma suíte determinística registra os resultados. Identifique o que são regras locais e o que seria um agente opcional do Dialogflow.
  5. Uma entidade e integração segura. Objetivo: acrescentar um sinônimo de curso e documentar seu equivalente no tipo de entidade course do Dialogflow ES. Critério de conclusão: testes retornam o valor canônico e tratam o curso desconhecido; qualquer extensão remota deve passar pelo seu servidor autenticado, com sessão isolada e nenhuma chave de conta de serviço no cliente.
